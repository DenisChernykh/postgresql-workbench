# Программа обучения

## Граница курса

Под «всеми аспектами» здесь понимается полный путь прикладного разработчика,
который работает с реляционной БД: модель данных, SQL, интеграция с приложением,
целостность, конкурентность, производительность, изменение схемы, безопасность,
диагностика, backup/restore и базовое масштабирование.

Это не попытка заучить каждую функцию PostgreSQL. После основной программы можно
отдельно сравнить документные, key-value, колоночные и графовые БД и понять, для
каких нагрузок реляционная модель перестаёт быть лучшим выбором.

Большинство уроков использует общий постоянный PostgreSQL. Но эксперименты,
которые меняют весь кластер (`pg_hba.conf`, WAL/PITR, replication, failover,
намеренный crash, `ALTER SYSTEM`, major upgrade), получат собственный временный
PostgreSQL и отдельный volume. Ломать общий учебный сервер ради изучения recovery
небезопасно и педагогически запутанно.

## Формат одного урока

Каждый каталог урока содержит:

```text
README.md       — ментальная модель, разбор, вопросы и упражнения
bootstrap.sql   — отдельная database и роль урока
schema.sql      — схема и подробно прокомментированный SQL
main.py         — небольшой пример с ручным SQL
compose.yaml    — постоянный Python-контейнер текущего урока
smoke.sh        — один сквозной запуск и проверка результата
```

Один урок раскрывает один основной механизм. Ориентир — 30–60 минут и не больше
50–100 строк существенного кода. В каждом уроке есть намеренная поломка: важно не
только увидеть happy path, но и понять наблюдаемую ошибку и способ восстановления.

Урок закончен, если ученик может:

- до запуска предсказать результат;
- объяснить, где находится транзакционная граница;
- назвать инвариант, который защищает схема или код;
- изменить пример без копирования готового решения;
- получить `SMOKE OK` после запуска с чистого состояния урока.

## Основной маршрут

Номер тематического блока и номер практического урока не обязаны совпадать:
первый вводный пример уже объединяет среду, соединение и базовый CRUD.

- Урок 001 реализует вводную часть блоков 00, 02 и 06.
- Урок 002 реализует основу блока 01: `NULL`, constraints и связь через FK.

Текущий следующий lesson:

- **Урок 003 — получение связанных данных:** `INNER JOIN`, `LEFT JOIN`, агрегаты,
  `GROUP BY` и `HAVING` на модели проектов и задач. Подзапросы, CTE и set
  operations останутся отдельным продолжением блока 03, чтобы пример можно было
  перепечатать за один подход.

После реализации lesson 003 этот указатель нужно заменить следующим конкретным
lesson, а строку о покрытии нового урока добавить в список выше.

| Блок | Темы | Практический результат |
|---|---|---|
| 00. Среда и ментальная модель | container, PostgreSQL server/cluster, database, schema, table, client, session, Docker network, volume, `psql` | Отличаем остановку клиента от остановки сервера; данные переживают пересоздание контейнера |
| 01. Реляционная основа | таблицы, строки, столбцы, типы, `NULL`, identity, PK, `UNIQUE`, `CHECK`, FK | Корректные данные записываются, противоречивые отвергаются самой БД |
| 02. CRUD и параметры | `INSERT`, `SELECT`, `UPDATE`, `DELETE`, `RETURNING`, фильтрация, сортировка, параметризованные запросы | Python безопасно записывает строку с кавычками без склейки SQL |
| 03. Получение данных | `JOIN`, агрегаты, `GROUP BY`, `HAVING`, подзапросы, CTE, set operations | Получаем отчёт из нескольких связанных таблиц |
| 04. Аналитический SQL | оконные функции, ranking, moving average, gaps and islands | Считаем рейтинг и накопительные итоги без циклов Python |
| 05. Моделирование | связи 1:1, 1:N, M:N, естественные и суррогатные ключи, нормальные формы, осознанная денормализация | Модель не допускает сиротские и двусмысленные записи |
| 06. Python DB-API | connection, cursor, row, transaction, commit/rollback, обработка ошибок, batch, `COPY` | Понимаем жизненный цикл соединения и не оставляем `idle in transaction` |
| 07. ACID и транзакции | атомарность, rollback, savepoint, ограничения в конце statement/transaction | Ошибка второй операции откатывает целый бизнес-сценарий |
| 08. MVCC и конкурентность | snapshots, уровни изоляции, lost update, row locks, deadlock, retry | Два клиента не нарушают инвариант остатка или баланса |
| 09. Идемпотентность | `UPSERT`, unique idempotency key, optimistic/pessimistic locking, advisory locks | Повтор команды не создаёт второй заказ или платёж |
| 10. Изменение схемы | ручные миграции, expand/contract, backfill, defaults, блокирующий DDL, совместимость версий приложения | Обновляем непустую БД без потери данных и долгой остановки |
| 11. Индексы и planner | B-tree, hash, GIN, GiST, составные/частичные/expression/covering indexes, statistics, `EXPLAIN (ANALYZE, BUFFERS)` | Не «добавляем индекс наугад», а сравниваем план и стоимость записи |
| 12. Производительность приложения | N+1, round trips, pagination, keyset pagination, prepared statements, pool, timeouts | Ускоряем сценарий и сохраняем правильный результат |
| 13. Возможности PostgreSQL | JSONB, arrays, full-text search, views, materialized views, partitioning | Выбираем специальный механизм по нагрузке, а не по моде |
| 14. Безопасность | роли, ownership, `GRANT`/`REVOKE`, schema privileges, secrets, SQL injection, RLS | Прикладная роль не делает DDL и не читает данные другого tenant |
| 15. Эксплуатация | activity, locks, logs, slow queries, statement/lock/idle timeouts, `VACUUM`, autovacuum, bloat, connection limits | Находим блокирующий PID и объясняем причину деградации |
| 16. Надёжность | `pg_dump`, `pg_restore`, физические backup, WAL, PITR, RPO/RTO | Восстанавливаем отдельную БД и проверяем контрольные суммы/количества |
| 17. Масштабирование | read replicas, replication lag, read-after-write, failover, logical replication, CDC, pooling, partitioning/sharding trade-offs | Понимаем, какие гарантии теряются при чтении с replica |
| 18. Итоговая лабораторная | каталог, склад, заказ, платёж, outbox, конкурентные повторы, миграция, диагностика, restore | Сохраняем деньги и остатки, выдерживаем повтор и восстанавливаем данные |

## Дополнительные лабораторные

После основного маршрута:

- PostGIS и геопространственные индексы;
- logical decoding и CDC;
- outbox/inbox и очереди;
- time-series workloads;
- OLTP против OLAP, звёздная схема и колоночные хранилища;
- сравнение PostgreSQL с Redis, MongoDB и графовой БД на одном workload;
- обновление major-версии PostgreSQL и проверка совместимости.

## Библиотеки, которые появятся позже

Сначала используется только Psycopg 3 и ручной SQL. Затем по одной причине за раз:

- `psycopg_pool` — ограниченный пул соединений;
- `asyncpg` — отдельное сравнение async-драйвера;
- SQLAlchemy Core — программная сборка запросов;
- SQLAlchemy ORM — identity map, unit of work и связи объектов;
- Alembic — история и применение миграций;
- `pytest` и Testcontainers — полноценные интеграционные тесты, если они понадобятся.

ORM имеет смысл добавлять только после того, как SQL, транзакции и планы запросов
стали наблюдаемыми и понятными. Иначе удобный API скрывает наиболее важные ошибки.
