# Как добавлять новый lesson в курс

Под новой таской курса в этом проекте понимается новый lesson — каталог
`lessons/NNN-topic`. Он должен быть самостоятельным учебным примером: теория
рядом с кодом, отдельные database и роль, постоянный Python-контейнер и один
реальный smoke.

Новый lesson создаётся только после предыдущего номера и раскрывает один главный
механизм БД. Полные правила для Codex записаны в корневом `AGENTS.md`; ниже — тот
же процесс в форме человеческой пошаговой инструкции.

## 1. Выбрать следующую тему

1. Открой `docs/LEARNING_PLAN.md`.
2. Прочитай явное сопоставление готовых уроков и тематических блоков в начале
   основного маршрута.
3. Если указан «Текущий следующий lesson», используй его. Иначе найди первую
   тему, которая ещё не раскрыта отдельным примером.
4. Проверь последний номер в `lessons/` и возьми следующий без пропуска.
5. Сформулируй один главный результат урока одним предложением.

Например, формулировка «получить отчёт через JOIN, GROUP BY и HAVING» достаточно
узкая. Формулировка «изучить весь SQL» слишком большая для одного lesson.

Перед кодом ответь на пять вопросов:

- Какой инвариант или механизм изучаем?
- Какие минимальные таблицы и данные его показывают?
- Как выглядит успешный сценарий?
- Какую одну ошибку ученик вызовет намеренно?
- Каким запросом smoke независимо докажет результат?

Если на последний вопрос нет точного ответа, пример пока спроектирован
недостаточно наблюдаемо.

## 2. Создать каркас

Формат имени:

```text
lessons/NNN-kebab-case-topic
```

В каталоге обязательны шесть файлов:

```text
README.md       # объяснение и порядок практики
bootstrap.sql   # database и непривилегированная роль
schema.sql      # схема урока
main.py         # пример на Python и ручном SQL
compose.yaml    # постоянный Python-контейнер
smoke.sh        # сквозная проверка на реальном PostgreSQL
```

Для номера `NNN` используй согласованные имена:

| Объект | Значение |
|---|---|
| Compose project | `bd-training-lesson-NNN` |
| Database | `lesson_NNN` |
| Login-role | `lesson_NNN_app` |
| Учебный пароль | `lesson_NNN_password` |
| Practice-каталог | `practice/NNN-kebab-case-topic` |

Последний готовый lesson можно использовать как структурный образец, но нужно
проверить каждое имя: случайно оставшиеся database, роль или путь предыдущего
урока нарушат изоляцию.

## 3. Написать `bootstrap.sql`

Bootstrap выполняется ролью `training_admin`, а не приложением. Он должен
повторно запускаться без ошибки и приводить инфраструктуру урока к ожидаемому
состоянию.

Обязательные свойства:

- `\set ON_ERROR_STOP on`;
- login-role имеет `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION
  NOBYPASSRLS`;
- роль и database создаются только при отсутствии;
- для `CREATE ROLE` и `CREATE DATABASE` используется проверка системного каталога
  и `\gexec`, потому что у этих команд нет подходящего универсального
  `IF NOT EXISTS`;
- повторный `ALTER ROLE` восстанавливает ожидаемые password и безопасные флаги,
  даже если роль меняли в ручном эксперименте;
- повторный запуск восстанавливает ожидаемые owner и право `CONNECT`;
- `PUBLIC` не получает неявный доступ к database урока.

Приложение никогда не должно получать строку подключения `training_admin`.

## 4. Спроектировать `schema.sql`

Схема должна быть минимальной для темы урока. Каждое ограничение, индекс или
связь добавляется только тогда, когда пример показывает его пользу.

Правила:

- подробно комментируй гарантию, а не очевидный синтаксис;
- давай важным constraints явные стабильные имена;
- показывай разницу между правилом приложения и гарантией PostgreSQL;
- пересоздавай только объекты текущего урока;
- учитывай порядок удаления таблиц с внешними ключами;
- не добавляй «на будущее» столбцы и абстракции, не участвующие в примере.

Схема practice-версии всегда лежит рядом с её `main.py`. Поэтому Python должен
искать её относительно `__file__`, а не текущего каталога процесса.

## 5. Написать `main.py`

На старте курса разрешены стандартная библиотека Python, Psycopg 3 и ручной SQL.
ORM и новые зависимости добавляются только ради отдельной учебной темы.

В примере должны быть видны:

- получение `DATABASE_URL` из окружения;
- открытие и закрытие connection/cursor;
- точные транзакционные границы;
- параметризованные значения через API драйвера;
- успешный сценарий;
- наблюдаемая ошибка или намеренный эксперимент;
- итоговое чтение данных.

Не вставляй значения в SQL через f-string. Комментариями объясняй, что будет
зафиксировано, что откатится и что увидит другое соединение.

Если файл приближается к нескольким сотням строк, сначала попробуй уменьшить
пример или разбить практику на этапы. Один урок должен оставаться пригодным для
ручного перепечатывания за 30–60 минут.

## 6. Настроить `compose.yaml`

Обычный lesson не создаёт собственный PostgreSQL. Он подключается к общей внешней
сети:

```text
bd-training-net
```

Внутренний адрес сервера:

```text
bd-training-postgres:5432
```

Python-сервис должен:

- собираться из `runtime/python/Dockerfile`;
- получать `DATABASE_URL` своей роли и database;
- монтировать корень курса как `/workspace`;
- использовать `working_dir: /workspace`;
- запускать `sleep infinity`;
- иметь `init: true`;
- не публиковать порт и не владеть общей сетью.

Так контейнер остаётся готовым для повторных `exec`, а завершение отдельного
Python-процесса не останавливает ни контейнер, ни PostgreSQL.

Кластерные эксперименты — WAL/PITR, replication, failover, `pg_hba.conf`, crash,
`ALTER SYSTEM`, major upgrade — являются исключением. Для них нужен отдельный
временный PostgreSQL и отдельный volume.

## 7. Написать `smoke.sh`

Smoke проверяет не внутреннее устройство функций, а один реальный сквозной
сценарий:

```text
bootstrap -> PostgreSQL -> Python -> COMMIT/ROLLBACK -> независимый SELECT
```

Обязательная последовательность:

1. `#!/usr/bin/env sh` и `set -eu`.
2. Вычислить корень репозитория, чтобы скрипт работал из любого каталога.
3. Принять первым необязательным аргументом относительный путь к practice
   `main.py`; без аргумента запускать эталон.
4. Проверить, что выбранный файл существует.
5. Выполнить `infrastructure up -d --wait` без остановки сервера.
6. Выполнить `bootstrap.sql` через административный `psql`.
7. До запуска выбранного файла убрать старое состояние только текущего урока.
   Иначе пустой practice-файл может ложно пройти на данных прошлого запуска.
8. Выполнить `lesson up -d app`, затем `exec -T app python <файл>`.
9. Новым соединением с `ON_ERROR_STOP` проверить зафиксированные данные и сам
   механизм урока: constraint, индекс, право, план или другое наблюдаемое
   свойство.
10. Сравнить точный результат и вывести понятный `SMOKE OK`.

Smoke не должен выполнять `down`, останавливать другие lessons или удалять общую
database/volume. Полноценные unit- и integration-тесты в этом курсе пока не
нужны.

После создания сделай файл исполняемым:

```bash
chmod +x lessons/NNN-kebab-case-topic/smoke.sh
```

## 8. Написать README lesson

README — часть урока, а не формальная справка. Добавь разделы:

1. цель;
2. ментальная модель или небольшой поток данных;
3. какие гарантии/механизмы показывает PostgreSQL;
4. что делает пример по шагам;
5. команды эталонного и practice-запуска;
6. порядок ручного перепечатывания небольшими этапами;
7. ожидаемый смысл вывода;
8. минимум одну намеренную поломку с прогнозом до запуска;
9. вопросы для самопроверки;
10. какие библиотеки решают похожую задачу в рабочих проектах и почему сейчас
    они не обязательны.

Не прячь объяснение только в комментариях к коду: ученик сначала читает README,
строит прогноз и лишь потом перепечатывает пример.

## 9. Обновить маршрут курса

После готового lesson:

- добавь ссылку в «Готовые уроки» корневого `README.md`;
- допиши в `docs/LEARNING_PLAN.md`, какую часть какого блока реализует новый
  номер;
- замени указатель «Текущий следующий lesson» следующим конкретным уроком;
- не объявляй большой блок полностью пройденным, если пример покрыл лишь основу.

Это позволяет следующему автору однозначно выбрать продолжение, не полагаясь на
историю предыдущего диалога.

## 10. Проверить готовность

Минимальная проверка:

```bash
sh -n lessons/NNN-kebab-case-topic/smoke.sh

docker compose -f lessons/NNN-kebab-case-topic/compose.yaml config

./lessons/NNN-kebab-case-topic/smoke.sh

docker compose -f lessons/NNN-kebab-case-topic/compose.yaml exec -T app \
  python -m py_compile lessons/NNN-kebab-case-topic/main.py

./lessons/NNN-kebab-case-topic/smoke.sh
```

Дополнительно проверь practice-путь и защиту от старых данных. Пустой временный
`main.py` не должен получить PASS только потому, что таблицы уже были заполнены
эталонным запуском.

Готовность означает:

- эталонный smoke проходит два раза;
- practice-файл можно запустить тем же smoke;
- роль урока непривилегированная;
- данные предыдущих lessons сохранены;
- общий PostgreSQL и Python-контейнер урока остаются работающими;
- комментарии и README позволяют понять пример без дополнительных догадок;
- Git commit/push не выполнены без отдельного запроса.

## Как поручить создание lesson Codex

Открой репозиторий курса и напиши:

```text
Создай следующий ещё не реализованный lesson курса.

Прочитай AGENTS.md, README.md и docs/LEARNING_PLAN.md. Создай ровно один новый
lesson, выполни реальный smoke дважды и проверь, что данные прошлых уроков не
затронуты. Автотесты не добавляй. Не делай commit и push без отдельного запроса.
```

Этого достаточно: подробные технические и педагогические правила уже находятся
в `AGENTS.md`.
