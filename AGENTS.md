# Инструкции Codex для курса по базам данных

Этот файл задаёт постоянные правила работы Codex в репозитории. Пользовательская
инструкция находится в `docs/HOW_TO_USE.md`.

## Назначение репозитория

Это последовательный практический курс по PostgreSQL и Python. Пользователь не
копирует готовые файлы, а перепечатывает `schema.sql` и `main.py`, запускает их и
объясняет наблюдаемое поведение. Поэтому читаемость, подробные комментарии и
небольшой размер урока важнее «production-ready» абстракций.

Главные источники истины:

- `docs/LEARNING_PLAN.md` — маршрут и границы курса;
- `README.md` — общая архитектура и список готовых уроков;
- уже созданные каталоги в `lessons/` — технический шаблон;
- README конкретного урока — его учебный контракт.

## Если пользователь просит следующий урок

1. Прочитай этот файл, `README.md`, `docs/LEARNING_PLAN.md` и два последних
   готовых урока.
2. Проверь `git status` и сохрани все несвязанные изменения пользователя.
3. Найди максимальный номер в `lessons/` и используй следующий номер без
   пропусков.
4. Возьми первую ещё не раскрытую тему из основного маршрута. Учитывай явное
   сопоставление уроков и блоков в начале `docs/LEARNING_PLAN.md`: один урок может
   покрывать часть нескольких блоков. Если там есть указатель «Текущий следующий
   lesson», он имеет приоритет над самостоятельным выводом из таблицы.
5. Если следующий механизм однозначен, сразу создавай урок. Задай вопрос только
   тогда, когда выбор существенно изменит учебный маршрут.
6. Один запрос на создание урока должен давать один новый lesson. Не объединяй
   несколько крупных тем ради скорости.

После реализации добавь урок в раздел «Готовые уроки» корневого `README.md`,
обнови сопоставление уроков с блоками и перенеси указатель «Текущий следующий
lesson» в `docs/LEARNING_PLAN.md`. Не объявляй весь блок пройденным, если урок
раскрыл только его часть.

## Обязательная структура урока

Каталог называется `lessons/NNN-kebab-case-topic` и содержит:

```text
README.md       — цель, ментальная модель, разбор и порядок практики
bootstrap.sql   — изолированные database и login-role урока
schema.sql      — схема с подробными комментариями
main.py         — небольшой пример на Python с ручным SQL
compose.yaml    — постоянный Python-контейнер урока
smoke.sh        — один сквозной запуск и проверка результата
```

Используй единое именование:

- Compose-проект: `bd-training-lesson-NNN`;
- database: `lesson_NNN`;
- login-role: `lesson_NNN_app`;
- учебный пароль: `lesson_NNN_password`;
- practice-каталог: `practice/NNN-kebab-case-topic`.

Каждый урок должен иметь собственные database и роль без `SUPERUSER`,
`CREATEDB`, `CREATEROLE`, `REPLICATION` и `BYPASSRLS`. Приложение подключается только своей ролью;
администратор `training_admin` используется лишь в `bootstrap.sql` и smoke.
Bootstrap должен быть повторяемым: для объектов без `IF NOT EXISTS` используй
проверку системного каталога и `psql \gexec`, а повторным `ALTER ROLE` возвращай
ожидаемые пароль и непривилегированные флаги.

## Общий PostgreSQL и контейнер Python

Обычные уроки подключаются к одному серверу из
`infrastructure/postgres/compose.yaml` через внешнюю сеть `bd-training-net` и
alias `bd-training-postgres:5432`.

Python-контейнер:

- собирается из `runtime/python/Dockerfile`;
- монтирует корень курса в `/workspace`;
- имеет `working_dir: /workspace`;
- запускает `sleep infinity` с `init: true`;
- остаётся работать после smoke, а каждый пример запускается через
  `docker compose exec app python ...`.

Не останавливай общий PostgreSQL и контейнеры других уроков. В smoke не должно
быть `docker compose down`. Команда `down -v` для общей инфраструктуры запрещена:
она удаляет все учебные базы.

Эксперименты, меняющие весь кластер, должны получить отдельный временный
PostgreSQL и отдельный volume. К ним относятся `pg_hba.conf`, WAL/PITR,
replication/failover, намеренный crash, `ALTER SYSTEM` и major upgrade. Не запускай
такие эксперименты на общем учебном сервере.

## Педагогический формат

Один урок объясняет один главный механизм и обычно занимает 30–60 минут.
Ориентир — 50–100 строк существенного кода, если тема позволяет.

В `schema.sql` и `main.py` комментируй не синтаксис сам по себе, а:

- какую гарантию даёт строка;
- где начинается и заканчивается транзакция;
- какое состояние остаётся после ошибки;
- почему выбран этот механизм;
- как наблюдать результат в PostgreSQL.

README урока обязан содержать:

1. цель и ментальную модель;
2. описание потока выполнения;
3. точные команды запуска;
4. поэтапный порядок перепечатывания;
5. ожидаемый смысл вывода;
6. минимум одну намеренную поломку с вопросом «что произойдёт до запуска?»;
7. вопросы для самопроверки;
8. раздел «Какие библиотеки используют в проектах».

Пока основной стек — стандартная библиотека Python, Psycopg 3 и ручной SQL.
Не добавляй ORM, миграционный фреймворк или новую зависимость без учебной причины.
Можно перечислить подходящие библиотеки в README и объяснить, какую задачу они
решают, не устанавливая их.

Всегда используй параметры драйвера для значений SQL. Не обучай склейке запросов
через f-string. Если динамическими являются идентификаторы, отдельно объясни
безопасную композицию SQL.

## Требования к smoke

Smoke — не набор unit-тестов. Он должен доказать, что реальная среда поднимается,
пример выполняется, а PostgreSQL сохранил ожидаемое состояние.

`smoke.sh` должен:

1. работать из любого текущего каталога;
2. принимать необязательный путь к `practice/.../main.py`;
3. до запуска проверять существование выбранного файла;
4. идемпотентно поднять общую инфраструктуру и выполнить `bootstrap.sql`;
5. очистить только состояние текущего урока до запуска выбранного файла, чтобы
   пустой или сломанный practice-файл не получил ложный PASS на старых данных;
6. поднять постоянный Python-контейнер и выполнить файл через `exec`;
7. отдельным соединением проверить зафиксированный результат и важный механизм
   урока, а не только текст, напечатанный Python;
8. завершиться ненулевым кодом при любой ошибке и вывести понятный `SMOKE OK` при
   успехе.

В SQL-проверках включай `ON_ERROR_STOP`. Проверяй ограничения, индексы или права
по их идентичности, а не только по общему количеству. Удаление старого состояния
должно быть строго ограничено database/объектами текущего урока.

Автотесты не добавляй: по запросу пользователя достаточно smoke-проверок.

## Проверка готового урока

Минимальная проверка перед передачей результата:

- `sh -n` для `smoke.sh`;
- разбор Compose-конфигурации через `docker compose ... config`;
- компиляция Python-файла;
- реальный smoke эталона;
- повторный smoke, доказывающий повторяемость и использование уже работающих
  контейнеров;
- smoke с заведомо пустым временным practice-файлом, если старые данные могли бы
  дать ложный PASS;
- проверка, что роль урока не получила административные права;
- проверка, что database и контейнеры прошлых уроков не были удалены.

Если Docker недоступен, не называй smoke успешным: явно отдели статические
проверки от непроверенного runtime.

Для нетривиального урока желательно провести независимое read-only ревью SQL,
Python, smoke и педагогики, затем исправить подтверждённые замечания.

## Границы изменений и отчёт

- Не меняй и не удаляй несвязанные файлы пользователя.
- Не сбрасывай базы прошлых уроков.
- Не делай Git commit или push без прямого запроса.
- В финальном отчёте укажи созданный урок, главный механизм, команды для
  эталонного и practice-smoke и точную границу проверки: статическая, Docker,
  PostgreSQL, Git.
