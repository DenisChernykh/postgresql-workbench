# Урок 002. Целостность данных и связи

## Цель

Научиться хранить бизнес-правила рядом с данными, чтобы их не мог случайно
обойти ни Python, ни другой сервис, ни ручной SQL.

Модель урока:

```text
projects (1) ────────< (много) tasks
                         project_id -> projects.id
```

Одна строка `projects` может иметь много `tasks`. Каждая задача обязана ссылаться
на существующий проект.

## Какие правила защищает PostgreSQL

| Механизм             | Правило урока                                | Ожидаемая ошибка Psycopg |
| -------------------- | -------------------------------------------- | ------------------------ |
| `NOT NULL`           | У задачи обязательно есть title              | `NotNullViolation`       |
| `CHECK`              | Title не пустой, priority находится в `1..5` | `CheckViolation`         |
| `UNIQUE`             | Код проекта не повторяется                   | `UniqueViolation`        |
| `FOREIGN KEY`        | Задача ссылается на существующий project     | `ForeignKeyViolation`    |
| `ON DELETE RESTRICT` | Project с задачами удалить нельзя            | `ForeignKeyViolation`    |

В `schema.sql` ограничения имеют явные имена. PostgreSQL возвращает эти имена в
структурированном поле `error.diag.constraint_name`, поэтому приложение может
понять причину без разбора текста ошибки.

Для `NOT NULL` в PostgreSQL 17 используется `error.diag.column_name`: у такого
ограничения таблицы ещё нет пользовательского имени в системном каталоге.

## `NULL` не равен пустой строке

- `NULL` означает, что значения нет или оно пока неизвестно;
- `''` — существующая строка длиной ноль;
- `'   '` — существующая строка из пробелов.

`NOT NULL` запрещает только первый вариант. Поэтому для title нужны одновременно:

```sql
title TEXT NOT NULL,
CONSTRAINT tasks_title_not_blank CHECK (btrim(title) <> '')
```

Отдельно `completed_at` оставлен nullable. Здесь `NULL` полезен и означает
«задача ещё не завершена». Не нужно запрещать `NULL` во всех столбцах подряд.

## Почему каждая ошибка получает отдельную транзакцию

После нарушения constraint PostgreSQL прерывает текущую транзакцию. Поймать
Python-исключение недостаточно: следующий SQL в той же транзакции получит
`InFailedSqlTransaction`, пока клиент не сделает `ROLLBACK` или не откатится к
savepoint.

В этом уроке `demonstrate_violation()` для каждой плохой команды открывает новое
соединение и после ожидаемой ошибки явно вызывает `connection.rollback()`.

На первой ошибке пример намеренно выполняет `SELECT 1` **до** rollback и получает
`InFailedSqlTransaction` с SQLSTATE `25P02`. Затем он делает rollback и успешно
выполняет `SELECT 1` на том же connection — это наблюдаемое доказательство
восстановления. Savepoint подробно появится в отдельном уроке про транзакции.

## Что делает пример

1. Пересоздаёт `projects` и `tasks` в одной транзакции.
2. Фиксирует один project и две валидные tasks.
3. По отдельности пытается записать `NULL`, пробельный title, priority `9`, duplicate
   code и ссылку на отсутствующий project.
4. Пытается удалить project, на который ссылаются tasks.
5. Для каждой ошибки печатает класс, SQLSTATE и диагностическое имя.
6. Новым соединением читает только валидные строки.

## Как перепечатывать

Создай два файла:

```text
practice/002-data-integrity/schema.sql
practice/002-data-integrity/main.py
```

Не перепечатывай большой `main.py` одним непрерывным блоком. Собери его по этапам:

1. Перепечатай `schema.sql`.
2. Добавь `read_schema()`, `create_valid_data()` и `print_valid_state()`. Временно
   вызови только создание и чтение валидных данных.
3. Добавь `demonstrate_violation()` и один случай `NOT NULL`; увидь `25P02` до
   rollback и успешный `SELECT 1` после него.
4. Добавь остальные пять вызовов — они повторяют уже понятный механизм для других
   constraints.

Типизация параметров helper — обычный Python-контракт, а не новая тема БД. Здесь
важно понять последовательность `SQL -> server error -> diagnostics -> rollback`.

Проверка собственного файла:

```bash
./lessons/002-data-integrity/smoke.sh practice/002-data-integrity/main.py
```

Если рядом с practice-версией `main.py` нет `schema.sql`, функция `read_schema()`
правильно завершится ошибкой: схема всегда относится к конкретному примеру.

## Ожидаемый смысл вывода

Сначала будут зафиксированы валидные строки. Затем шесть плохих операций будут
отклонены. Последние две намеренно получают одинаковые `ForeignKeyViolation`,
SQLSTATE `23503` и `tasks_project_fk`: один FK защищает связь и при вставке сироты,
и при удалении родителя. В конце останутся:

```text
5 | завершена | Разобрать ограничения
3 | открыта   | Перепечатать schema.sql
```

Smoke независимо проверит: один project, две tasks, одна открытая задача и ни
одной задачи без project.

## Намеренные эксперименты

### 1. Убрать `NOT NULL` у tasks.title

До запуска предскажи, пройдёт ли `NULL` через
`CHECK (btrim(title) <> '')`. Затем объясни разницу между результатами `FALSE` и
`UNKNOWN` в SQL.

### 2. Заменить `ON DELETE RESTRICT` на `ON DELETE CASCADE`

Предскажи поведение helper: `DELETE` станет допустимым, поэтому ветка `else`
сделает защитный rollback и завершит пример сообщением «Constraint не сработал».
Каскадные строки не зафиксируются именно из-за этого rollback. Верни `RESTRICT`
после наблюдения; отдельный урок позже сравнит политики удаления на commit.

### 3. Временно убрать `connection.rollback()`

Закомментируй rollback внутри `demonstrate_violation()` и предскажи результат.
Первый пробный `SELECT 1` по-прежнему даст ожидаемую `25P02`, а второй SELECT,
который должен был доказать recovery, тоже получит `InFailedSqlTransaction` и
остановит программу. После наблюдения обязательно верни rollback.

3. Почему `FOREIGN KEY` надёжнее проверки project в Python перед `INSERT`?
4. Как один `FOREIGN KEY` защищает связь и при INSERT задачи, и при DELETE проекта?
5. Почему после constraint error нужен `ROLLBACK` или savepoint?
6. Чем `RESTRICT` отличается от осознанно выбранного `CASCADE` для данных?

## Какие библиотеки используют в проектах

Новых зависимостей в уроке нет: Psycopg 3 и ручной SQL достаточно.

- SQLAlchemy описывает constraints в metadata, но исполняет их PostgreSQL;
- Alembic добавляет и изменяет constraints через миграции;
- Pydantic может раньше проверить входные данные, но не заменяет ограничения БД;
- Psycopg предоставляет отдельные классы ошибок и поля `diag`.

Главный принцип: валидация приложения делает ошибку удобной для пользователя,
а constraint базы гарантирует целостность для всех путей записи.
